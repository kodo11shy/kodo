## 0. 现状诊断：当前数据流全景

### 老师端页面与数据生产

| 页面 | 产生什么数据 | 是否关联到具体孩子 | 是否自动沉淀到成长档案 |
|------|------------|:---:|:---:|
| 签到签退 | checkin_time / checkout_time / pickup_person | ✅ | ✅ 出勤天数 |
| 拍照 → 关联学生 | 照片 + photo_type + 学生关联 | ✅ | ✅ 照片墙 |
| 作业 → 拍照 → 批改 → 改错 | homework 记录 + score + 三阶段照片 | ✅ | ✅ 时间线 |
| 餐食 → 关联学生 | menu_text + 照片 + 学生备注 | ✅ | ✅ 时间线 |
| 成长档案 → 写评语 | content + mood_tag | ✅ | ✅ 时间线 |
| 学生管理 | 基本信息 / 家长 / 健康 / 接送人 | ✅ | 基础档案 |

### 家长端看到什么

| 模块 | 数据来源 | 展示形式 |
|------|---------|---------|
| 首页今日动态 | `/parent/dashboard/today` API | 今日瞬间(照片) + 今日餐食 + 最新作业 + 最新评语 |
| 成长档案 | `/parent/growth/{id}` API | 概览(出勤/均分/作业数) + 30 天时间线 |
| 作业记录 | `/parent/homework/{id}` API | 按日期筛选，展示三步闭环照片 |
| 照片墙 | `/parent/photos/{id}` API | 网格展示，按 photo_type 标颜色 |

### 核心问题：数据是散的，观察是缺的

```
当前状态：

  签到 ───→ 出勤天数统计
  拍照 ───→ 照片库 ─→ 家长看到一张照片,不知道这张照片"说明什么"
  作业 ───→ score/error_count ─→ 家长看到分数,不知道"孩子今天写作业的状态"
  餐食 ───→ 吃了什么 ─→ 家长看到菜单
  评语 ───→ 一段文字 ─→ 最接近"观察",但碎片化,无场景无标签

目标状态：

  签到 ───→ 到班情绪/状态观察
  拍照 ───→ 标注"这个瞬间体现了什么能力/品质"
  作业 ───→ 作业完成状态标签(专注/粗心/进步/薄弱)
  餐食 ───→ 特殊情况标记(挑食/胃口好/过敏提醒)
  评语 ───→ 结构化为"一句话+场景+标签+是否家长可见"
```

## 1. 现有老师端功能是否符合"日常留痕"的使用逻辑？

**部分符合，但不自然。**

**符合的部分：**

- 签到签退、作业三步闭环、餐食记录、评语——这些都是老师本来就要做的事
- 这些操作天然生成数据，无需老师额外填表
- 后端已有 timeline 机制把数据聚合到孩子时间线

**不符合的部分：**

- **没有"这个数据留给孩子什么观察"的意识**——老师拍完照、改完作业，不知道自己正在"积累观察"
- **照片库"重后期处理"**：上传 → 关联学生 → 选标签 → 标记精选，四个步骤都是事后操作，未嵌入工作流
- **作业信息只在"作业页面"被看见**，批改时老师对孩子的判断（专注/粗心/进步了）没有机会记录下来
- **评语入口太深**：老师要写评语，需要走 工作台 → 成长档案 → 选择一个孩子 → 点写评语 → 弹窗填写。路径 4~5 步

**核心矛盾**：老师日常操作产生的数据量足够（签到、照片、作业、餐食），但这些数据缺乏"观察注解"。孩子在某个场景下的真实表现，存在于老师的脑海里，没有被系统引导着记录下来。

## 2. 哪些页面会增加老师负担？应该如何简化？

### 评估矩阵（按负担从高到低）

| 页面 | 当前操作复杂度 | 主要负担点 | 简化方向 |
|------|:------------:|-----------|---------|
| **拍照页** | 🔴 高 | 单张拍→上传→跳转学生选择器→关联→设标签，流程断裂 | 拍照时默认"快速记录"，一键拍照即自动关联签到状态 |
| **餐食记录** | 🟡 中高 | 填菜单+上传照片+选关联学生(默认选中但可调整) | 接受现状，但增加"个别学生备注"的快捷添加 |
| **照片库** | 🟡 中 | 长按→标签/精选/关联，批量操作入口多 | 保留，作为"精细管理"入口，不做高频修改 |
| **成长档案→写评语** | 🟡 中 | 入口深(3级页面)，弹窗输入，只有 4 个 mood 选项 | 在作业批改完成、签到等关键节点"顺带提醒" |
| **作业→批改** | 🟢 中低 | 需要评分+拍照+写备注，本身就是老师工作 | ✅ 合理，不做变动 |
| **签到签退** | 🟢 低 | 点击学生名字即可 | ✅ 合理，不做变动 |
| **作业→创建** | 🟢 低 | 选择学生→拍照→提交 | ✅ 合理，不做变动 |

### 关键负荷判断

**真正的负担不在于操作量，而在于"操作后的整理工作"**。老师拍照 3 秒，上传+关联学生可能花 30 秒。

如果同一张照片能：
1. 拍照时自动关联到当天签到学生列表（"拍全班合影，关联所有人"）
2. 或者拍照后默认标记为"日常"，留待有空时再精确分类

这样压力就大幅降低了。

## 3. 签到、作业、照片、餐食、评语如何自然沉淀孩子资料？

### 现状 vs 目标

| 页面 | 当前沉淀方式 | 可自然强化的方式 |
|------|------------|----------------|
| **签到** | 记录到/离时间 | 到班时增加一个"情绪状态"轻量标记（😊 开心 / 😐 平静 / 😢 不情愿），不增加操作，只增加一个点选 |
| **作业（批改完成时）** | 只记录分数和错题数 | 批改完成弹出"完成状态标签"（专注/粗心/进步/薄弱/认真），0.5 秒点选 |
| **拍照（关联学生时）** | 设置 photo_type 标签 | 增加"成长维度"可选：社交/学习/运动/生活/情绪/作品 |
| **餐食（记录时）** | 记录菜单和照片 | 记录"个别学生用餐情况"作为观察备注 |
| **评语** | 纯文本 + mood_tag | 结构化：场景(课堂/作业/餐食/活动) + 标签 + 内容 + 是否可见家长 |

### 沉淀数据流示意

```
老师日常操作流：

  签到
    └─→ 到班状态(可选)

  作业批改完成
    ├─→ score + error_count(已有)
    └─→ 作业态度标签(新增,可选)

  拍照
    ├─→ photo_type(已有)
    └─→ 成长维度标签(新增,可选)

  餐食记录
    └─→ 个别学生用餐备注(已有,但未显式作为观察)

  写评语
    ├─→ 内容 + mood_tag(已有)
    └─→ 场景 + 多标签 + 家长可见开关(改进)

           ↓  ↓  ↓

  【孩子资料库】 ← 所有数据自动归集
     ├─ 基础档案(姓名/年级/家长/健康)
     ├─ 月度统计(出勤/作业/均分)
     ├─ 时间线(所有操作的时间流)
     └─ 观察记录(老师确认过的观察条目)
```

## 4. 作业页是否应该增加轻量观察标签？

**应该加。但时机和形式是成败关键。**

### 为什么应该加

当前作业批改页面已经有评分(1-10)和错题数，但这两个数字只能反映"作业正确率"，完全不能反映"孩子做作业时的状态"：

- 一个孩子得了 10/10，可能是自己认真做的，也可能是抄的
- 一个孩子得了 5/10，可能是粗心，也可能是真的不会
- 一个孩子虽然错了但比昨天少错 3 题——这是进步，但系统不知道

老师批改时在心里已经有了这些判断，但没有地方记录。

### 怎么做才不打扰

**关键修正（v1.1）：从"事后弹出"改为"提交时一并保存"**

v1.0 的方案是"批改提交成功后再弹一行标签"，但反向审视发现：**批改完成后老师已经进入"下一件事"的心态，不会再回头点标签**。采纳率会从第一周 30~40% 快速衰减到 5~10%。

**修正后设计：**

1. **不增加新页面**——不改动作业详情页 WXML 整体结构
2. **标签放在"保存批改"按钮同一区域**——老师在提交批改前就能看到标签行，勾选标签和提交批改是一个连贯动作，不是两步
3. **标签行紧贴评分区下方**，自然融入批改流程：

   ```
   ⭐评分: ★★★★★★★★★☆   错题: 3
   👀 完成状态: [专注] [粗心] [进步] [认真] [薄弱] [需要帮助]
   ┌─────────────────────────────────────┐
   │        ✅ 保存批改                     │
   └─────────────────────────────────────┘
   ```

4. **所有标签可选，不选不影响提交**——老师可以不选，但标签就在那里，视觉上起到了提示作用
5. **标签预设、可配置**——由管理员在系统配置中设置

### 标签集定义

为避免不同老师用词不一致，标签集必须预设且含义清晰：

| 标签 | 含义 | 使用场景举例 |
|------|------|------------|
| 专注 | 完成态度认真，一气呵成 | 作业工整、无涂改、全神贯注完成 |
| 粗心 | 有计算/抄写错误，非知识点问题 | 数字抄错、竖式错位、标点遗漏 |
| 进步 | 相比前次有明显改善 | 字迹变工整了、错题减少了、速度提高了 |
| 认真 | 虽然结果不完美但态度端正 | 字迹工整、步骤完整、努力完成了 |
| 薄弱 | 特定知识点掌握不牢 | 某类题型反复出错、概念混淆 |
| 需要帮助 | 需要老师额外辅导 | 完全不会做、空题较多、理解困难 |

**注意**："粗心"和"薄弱"不应作为标签呈现给家长（见第 11 节可见性分级修正）。

### 数据模型示意

现有 `HomeworkRecord` 增加字段：`observation_tags: str[]`（可选数组，存储标签 key 如 `["focused", "improved"]`）

## 5. 餐食页是否应该默认记录正常情况，只让老师标记特殊孩子？

**非常应该。这是典型的"默认正常→例外标记"模式。**

### 当前状况

餐食页已经做得不错：每天一条记录，菜单+照片+关联学生。但存在两个问题：

1. **关联学生是全选的**（已签到学生默认选中），但老师无法快速标记"谁没吃好"
2. **餐食记录停留在"今天吃了什么"**，没有上升到"孩子饮食观察"

### 建议设计

餐食记录时：

- **默认所有签到学生为 "🍚 正常用餐"**
- 老师只需点击个别学生，标记例外：
  - 「😋 吃得很好」
  - 「😐 吃得少」
  - 「🤢 挑食」

**这样不增加老师负担**（大部分孩子不用操作），同时**沉淀了饮食维度的观察**。

### 重要修正（v1.1）：过敏提醒与日常观察分离

v1.0 方案把 "⚠️ 过敏提醒" 和挑食/饭量并列作为餐食标签，这是错误的。

**原因**：

- 过敏是**安全信息**，不是观察性记录。如果一个孩子有过敏史而老师忘了打标签，风险极高
- 过敏信息应该来自**学生健康档案**（已在 `student-detail` 页的健康 tab 中），而非老师每天的餐食记录
- 把过敏和挑食放在一起选择，容易让老师混淆"观察"和"告警"

**修正方案**：

- 餐食标签仅保留观察性内容：正常 / 吃得很好 / 吃得少 / 挑食
- 过敏提醒改为**系统自动触发**：当某个有过敏史的孩子在餐食关联列表中出现时，自动在老师界面上显示红色过敏角标，并提示"请确认该生今日菜品不含过敏源"
- 过敏确认记录进入孩子的安全日志，而非观察记录

### 例外标记的前端交互示意

```
学生列表（默认全部 "🍚 正常"）：

[🍚 正常] 张三    [🍚 正常] 李四    [😋 很好] 王五
[🍚 正常] 赵六    [😐 少] 陈七      [🤢 挑食] 刘八

点击学生名称 → 循环切换: 正常 → 很好 → 少 → 挑食 → 正常
```

只点需要标记的孩子，其他孩子走默认，**一个班 15 人只需操作 2~3 次点击**。

## 6. 照片库如何从"相册"变成"成长证据库"？

### 现状分析

照片库当前功能是完整的：

- photo_type: 日常 / 活动 / 作业 / 餐食 / 生活（5 种）
- is_featured 精选标记
- 关联学生
- 标签修改
- 批量操作

**但"为什么存这张照片"的意图没有表达。** 家长看到一张孩子做手工的照片，只能看"一张照片"，不知道老师想通过这张照片传达什么。

### 改进建议

1. **在现有 photo_type 基础上增加"成长维度"标签**（新增可选字段）

   | 维度 | 含义 | 典型场景举例 | 非典型(避免误标) |
   |------|------|------------|----------------|
   | 社交合作 | 与同伴互动、合作、分享 | 小组搭积木、合作画画、分享零食 | 独自安静活动不属此类 |
   | 学习专注 | 独立完成任务、专注投入 | 认真写作业、专注阅读、做练习题 | 集体游戏打闹不属此类 |
   | 运动协调 | 大肌肉/小肌肉运动、手眼协调 | 跳绳、拍球、做操、精细手工 | 坐着听讲不属此类 |
   | 生活自理 | 独立照顾自己、生活习惯 | 自己吃饭、穿鞋、收拾书包 | 被老师喂饭不属此类 |
   | 情绪表达 | 情感体验和表达 | 开心大笑、认真思考表情、分享快乐 | 哭闹发脾气的照片不宜上传 |
   | 创意作品 | 产出性创造活动 | 绘画、泥塑、折纸成品、搭建作品 | 作业本不算创意作品 |

   **v1.1 修正**：v1.0 只列了维度名，没有定义边界。加上正例/反例后，老师标记一致性会显著提升。

2. **标记维度的时机：拍照 → 关联学生这一步**
   - 当前"拍照→关联学生"页面只设 photo_type
   - 增加一栏"这张照片体现了什么？（可选）"
   - 老师不选则走默认，选了则成为"成长证据"

3. **精选（is_featured）的含义更加明确**：精选照片 = 本学期代表性成长证据

4. **家长端照片墙按维度分组展示**，而非简单按时间倒序
   - "社交小能手"、"创意作品"、"运动时刻"——不同维度分栏
   - 避免流水账刷屏
   - **v1.1 修正**：此改动的前置条件是"每个孩子至少积累了 10 条以上维度标记"，否则按维度分组的展示效果不如时间线。因此，第一阶段的家长端不必改动，留到第二阶段数据充裕后再切换。

## 7. 老师评语如何做成"一句话 + 场景 + 标签 + 是否家长可见"？

### 当前评语的问题

评语表 `TeacherRemark` 当前字段：

```
content: str        # 评语内容
mood_tag: str       # 开心/进步/鼓励/注意(单选)
record_date: date   # 日期
```

不足：

- **mood_tag 是情绪标签，不是场景标签**——家长看到"开心"，不知道是在什么场景下开心的
- **评语要么都能看，要么都不看**——没有"老师内部笔记 vs 给家长看"的分级
- **评语入口深**——老师很少专门去"写评语"，导致评语量少

### 建议的评语结构

| 字段 | 类型 | 说明 | 必填? |
|------|------|------|:----:|
| content | text | 一句话观察 | 是 |
| scene | enum | 场景：课堂 / 作业 / 餐食 / 活动 / 签到 / 其他 | 否 |
| tags | str[] | 多标签：认真 / 进步 / 粗心 / 社交 / 分享 / 情绪 | 否 |
| visible_to_parent | bool | 是否家长可见 | 否(默认 true) |
| mood_tag | str | 保留现有心情标签 | 否 |

### 不给老师增加负担的方式

- **场景和标签都不必每次都填**——简化到"一句话 + 是否家长可见"即可
- **填入入口不限于"成长档案"**——在作业批改完成时、拍照关联时、餐食记录时，都可以轻量触发"一句评语"
- **AI 辅助提炼摘要**（第二阶段）：老师每天产生多个操作，AI 自动生成一条当日观察摘要，老师确认后发送给家长

### 家长可见性设计

- 默认 `visible_to_parent = true`
- 老师可以关闭某条评语的家长可见（用于内部记录）
- 家长端只能看到 `visible_to_parent = true` 的评语
- 老师端标注"仅老师可见"的标识

### v1.1 重要补充：使用规范（不可只有技术开关）

v1.0 只设计了功能开关，但反向审视发现：**只有技术开关没有使用规范，会造成社交压力和信任问题。**

**建议的使用规范**：

- `visible_to_parent = false` 的用途仅限于：老师记录尚不成熟的想法、需要与其他老师沟通的内部关注、等待更完整信息后再决定如何描述的观察
- 不应长期使用：如果一条评语标记为不可见，建议在 48 小时内决定是修改后可见、还是删除
- 老师需要知道：**如果家长问起来"今天有什么想说的"，老师可以直接回答"有的，我还在整理，晚点会发给你"**——而不是陷入"有但不能给看"的尴尬
- 建议机构层面约定：`visible_to_parent = false` 的比例不超过总评语的 10%，超出时应提醒老师复核

**技术设计上的配合**：

- 老师端列表页区分显示：可见评语用普通样式，不可见评语用灰色/斜体并标注"仅内部"
- 不可见评语在 48 小时后自动提醒老师"是否确认或删除"
- 家长端完全看不到不可见评语的存在——不显示计数、不显示"有隐藏内容"的暗示

## 8. 老师端是否需要一个"今日观察候选"页面？

**需要。这是整个系统从"数据"到"观察"的关键转换页。**

### 为什么需要

当前老师在一个孩子身上产生了 5 种数据（签到、照片、作业、餐食、评语），但这些数据分布在 5 个页面。老师没有在一个地方"看到这个孩子今天完整的样貌"。

换句话说，**数据已经沉淀了，但观察没有汇总。**

### 页面设计原则

不是"新增一个填表页面"，而是**把今天已有的数据变成一条条候选观察**：

```
┌─────────────────────────────────────────────┐
│  今日观察候选                   2026-06-18   │
│                                              │
│  ┌─────────────────────────────────────────┐ │
│  │ 👦 张三                         5条记录 │ │
│  │   ✅ 签到 08:15 · 状态:开心             │ │
│  │   📚 语文作业 批改完成 · 得分 8/10       │ │
│  │   📸 2张照片 · 手工课作品                │ │
│  │   🍚 餐食正常 · 标注:吃得很好            │ │
│  │   ✏️ 评语:今天上课举手很积极             │ │
│  │  [🤖 生成观察摘要] [编辑] [确认发送]     │ │
│  └─────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────┐ │
│  │ 👦 李四                         2条记录 │ │
│  │   ✅ 签到 08:05 · 状态:不情愿           │ │
│  │   📚 数学作业 批改完成 · 得分 6/10       │ │
│  │   → 需关注:今天到班情绪不高,作业粗心    │ │
│  │  [🤖 生成观察摘要] [编辑] [确认发送]     │ │
│  └─────────────────────────────────────────┘ │
│                                              │
│  📌 此页面仅老师可见,确认后数据进入孩子资料库 │
└─────────────────────────────────────────────┘
```

### 关键设计点

1. **候选观察 = 今日所有数据自动归集**，老师不需要手动添加
2. **AI 摘要**（第二阶段）——点击生成一段自然语言观察，老师修改后确认
3. **编辑**——老师可以增删改标签，调整"是否家长可见"
4. **确认**——确认后的观察进入孩子资料库的"观察记录"部分
5. **不确认也不丢失**——今天的数据仍保留在时间线中，只是未成为"正式观察"

### 准入时机

**此完整页面放在第三阶段。** 第一阶段只沉淀数据，第二阶段建立索引，第三阶段才做聚合页面。

### v1.1 修正：阶段间需要衔接机制

v1.0 把"今日观察候选页面"放到第三阶段，但第一阶段只加字段不做确认——这会导致数据沉淀了但无人确认。

**修正方案**：第一阶段增加一个极轻量的"待确认"入口，作为阶段一到阶段三的桥梁：

1. **老师工作台（dashboard）增加角标**——在"成长档案"图标右上角显示当日待确认计数
2. **角标计数规则**：当天产生了标签/标记但尚未确认的记录数
3. **点击角标不跳新页面**——进入现有的"成长档案"页面，在顶部增加一行"今日有 N 条待确认观察"
4. **确认操作在现有页面完成**——老师在成长档案中看到某条记录，点击可将其标记为"已确认"

```
工作台示意图：

  ┌──────┐  ┌──────┐  ┌──────┐
  │ 拍照  │  │照片库 │  │ 签到  │
  └──────┘  └──────┘  └──────┘
  ┌──────┐  ┌──────┐  ┌──────┐
  │ 作业  │  │成长档 │  │ 餐食  │
  │       │  │案 🔴3│  │       │
  └──────┘  └──────┘  └──────┘
              ↑ 角标提示有 3 条待确认
```

这样在阶段一和阶段三之间建立了一个自然的衔接：老师每天在成长档案页面顺手确认几条观察，为后续的聚合和 AI 摘要打基础。

## 9. 家长端如何展示成长观察？

### 当前问题

家长端成长档案（growth 页面）是一个**纯时间线**：

```
2026-06-18  语文 · 待批改    [时间线一条]
2026-06-18  老师评语          [时间线一条]
2026-06-17  数学 · 已完成     [时间线一条]
2026-06-16  餐食              [时间线一条]
```

这就是典型的"流水账"。家长刷完也不知道孩子这周在哪些方面有进步。

### 展示原则

1. **按能力维度归纳，而非纯时间倒序**
2. **正面引导，不比较孩子间差异**
3. **不说"孩子怎么样"，说"我们观察到什么"**

### 建议的家长端展示结构

```
┌─────────────────────────────────────────────┐
│  🌟 张三的成长档案                          │
│                                              │
│  --- 本月概览 ---                            │
│ 出勤 18天 | 作业 22次 | 均分 8.5            │
│                                              │
│  --- 成长观察(按维度)---                     │
│                                              │
│  📖 学习习惯                                 │
│    ✅ 6/15 数学作业完成认真,正确率提高       │
│    ✅ 6/12 语文作业字迹工整                  │
│                                              │
│  👫 社交情感                                 │
│    ✅ 6/14 和小朋友一起完成手工,主动分享     │
│                                              │
│  🍚 生活习惯                                 │
│    ✅ 6/13 独立吃完午餐,不挑食               │
│                                              │
│  🎨 创意表达                                 │
│    ✅ 6/10 绘画作品入选班级展示墙            │
│                                              │
│  --- 全部动态(时间线)---                     │
│  [可折叠区域,默认收起]                       │
└─────────────────────────────────────────────┘
```

### 关键设计原则

- **不贴标签**：不说"张三是个粗心的孩子"，说"6/15 数学作业出现了粗心错误"
- **重正面发现**：每条观察以正面或中性角度表述
- **基于事实**：每条观察都可追溯到原始数据（照片/作业/评语）
- **家长无需理解"内部概念"**：不出现 `photo_type=activity` 这样的内部术语

## 10. 家校沟通群的信息如何处理？

### 可见性分级

| 内容 | 老师端可见 | 家长端可见 | 说明 |
|------|:--------:|:--------:|------|
| 签到时间/签退时间 | ✅ | ✅ | 已有 |
| 接送人信息 | ✅ | ✅ | 已有 |
| 作业分数 | ✅ | ✅ | 已有 |
| 作业照片(三阶段) | ✅ | ✅ | 已有 |
| 餐食菜单/照片 | ✅ | ✅ | 已有 |
| 评语(visible_to_parent=true) | ✅ | ✅ | **建议新增字段** |

| "今日观察候选"页面 | ✅ | ❌ | 完全内部 |
| 健康信息(过敏/病史) | ✅ | ✅ | 已有 |
| 家长绑定状态 | ✅ | ❌ | 管理信息,与家长无关 |
| 资料完整度/待补标记 | ✅ | ❌ | 管理信息 |

### 原则

1. **老师产生的内容，默认家长可见**——评语、标签、照片等都是教育服务的一部分
2. **"老师的思考过程"不给家长看**——候选观察、内部标记、待办提醒
3. **健康/安全信息必须双向透明**——过敏、病史等

## 12. 第一阶段最小闭环建议

### 第一阶段目标

> **不改数据库核心结构、不新增独立页面、不引入 AI，只优化现有页面的交互，让老师在日常操作中自然产生"观察"。**

### v1.1 重要修正：真实工作量估算

v1.0 说"改 4 个页面"，但这只算了前端页面数，没算后端和数据库。以下是修正后的真实工作量：

| 改动项 | 前端文件 | 后端文件 | 数据库 | 预估人天 |
|--------|---------|---------|--------|:-------:|
| ① 作业批改标签（提交时一并选择） | `homework-detail.js` + `.wxml` | `homework.py` schema + route | HomeworkRecord 新字段 | 1~2 天 |
| ② 餐食例外标记（默认正常+安全角标） | `meal.js` + `.wxml` | `meals.py` schema + route | MealStudentNote 新字段 | 1~2 天 |
| ③ 照片成长维度标签 | `student-picker.js` + `.wxml` + `photolib.js` | `photos.py` schema + route | Photo 新字段 | 1~2 天 |
| ④ 评语可见性开关 | `growth.js` + `.wxml` | `remarks.py` schema + route | TeacherRemark 新字段 | 1 天 |
| ⑤ 工作台"待确认"角标（新增衔接机制） | `dashboard.js` + `.wxml` + `growth.js` | 后端聚合计数 API | 无（仅查询） | 1 天 |
| ⑥ 历史数据迁移脚本 | 无 | 独立 migration 脚本 | 批量设置默认值 | 0.5 天 |
| **合计** | **~8 个文件** | **~6 个文件** | **4 个新字段** | **5~8 天** |

**这不能再叫做"轻量改动"**——需要 1~2 周的集中开发周期。如果希望更短，需要在 ①~⑤ 中排优先级。

### 冷启动策略（v1.1 新增）

v1.0 假设"上线即产生数据"，没考虑历史数据空洞的问题。

**修正方案**：分三步处理冷启动

**第一步：历史数据默认标记（代码上线时执行一次）**

| 数据表 | 存量数据 | 默认值策略 |
|--------|---------|-----------|
| HomeworkRecord (已有 6 个月) | 约数百条 | 不对历史作业回填标签，新标签只从上线日起产生 |
| Photo (已有数百张) | 约数百张 | `dimension` 全部设为 null，现有 photo_type 保留不变 |
| MealStudentNote | 数十条 | `meal_status` 全部设为 null，表示"未启用新机制之前的记录" |
| TeacherRemark | 数十条 | `visible_to_parent` 全部设为 true（向前兼容） |

**第二步：上线后前 2 周——引导期**

- 不切换家长端展示，家长端看到的仍是旧时间线
- 老师端新增字段全部可选，老师自然适应
- 目标：2 周内让 50% 以上老师产生至少 1 次标签

**第三步：第 3~4 周——数据评估**

- 统计标签覆盖率（有标签的记录/总记录）
- 如果覆盖率 >30%，可以考虑进行家长端展示调整
- 如果覆盖率 <10%，需要分析原因并调整交互

### 采纳率兜底（v1.1 新增）

v1.0 的设计依赖"老师主动点标签"，但没有应对"老师不点"的预案。

**分层应对策略**：

| 采纳率 | 状态 | 应对方案 |
|:-----:|------|---------|
| >60% | ✅ 优秀 | 系统正常运行，按原计划推进第二阶段 |
| 30~60% | 🟡 可接受 | 观察趋势，如果是递减趋势就启动轻量引导 |
| 10~30% | 🟠 需干预 | 增加 teacher dashboard 上的"待标记"汇总提示，每周一次推送提醒 |
| <10% | 🔴 失效 | 回退设计方案——可能的方向：① 改"可选"为"每次提交时默认选中一个，老师可改" ② 取消标签，改为老师每天统一用自然语言写一段观察 |

### 建议改动（按优先级排列）

| 优先级 | 改动项 | 阶段 | 说明 |
|:-----:|--------|:----:|------|
| **P0** | 作业批改标签（提交时一并选择） | 第一周 | 最自然的观察时机，标签行融入现有表单 |
| **P0** | 餐食例外标记 + 过敏安全角标 | 第一周 | 默认正常，几乎零负担，过敏角标是安全需求 |
| **P1** | 评语可见性开关 | 第二周 | 简单，涉及家校信任边界，需搭配使用规范 |
| **P1** | 工作台"待确认"角标 | 第二周 | 阶段一到阶段三的衔接，无此机制则数据只沉淀不确认 |
| **P2** | 照片维度标签 | 第三周 | 维度的定义和使用需要老师培训，可稍晚 |
| **P2** | 家长端展示结构调整 | **第二阶段** | 等数据充裕后再改 |

### 第一阶段不改的

- ❌ 新增"今日观察候选"独立页面（留第三阶段）
- ❌ AI 生成摘要（需第二阶段数据积累 + 评估模型可行性）

### 修正后的数据效果预期（v1.1）

v1.0 说"每个孩子每天产生 2~3 条，一个月 40~60 条"——这是稳态理想值。

**修正后的更现实预期**：

| 阶段 | 时间 | 单个孩子日均标签数 | 全班(15人)日均标签数 | 场景 |
|:---:|:----:|:-----------------:|:------------------:|------|
| 引导期 | 第 1~2 周 | 0.3~0.8 | 5~12 | 老师在适应，部分人试用手动标记 |
| 习惯期 | 第 3~4 周 | 0.8~1.5 | 12~22 | 大部分老师已形成习惯 |
| 稳定期 | 第 2 个月 | 1.5~2.0 | 22~30 | 数据进入稳态 |
| 期望值 | 长期 | ~1.5 | ~22 | 每月每个孩子约 30 条结构化观察 |

30 条/月/孩子对于智能摘要来说属于**勉强够用但偏少**。这意味着：
- 第二阶段的 AI 摘要需要基于 30 条/月的密度设计（不能假设 60+）
- 摘要的粒度应该是"周报"而非"日报"
- 如果采纳率低于预期，AI 部分可能需要重新评估可行性

## 13. 方案反思考与补充（v1.1 新增）

### 13.1 为什么需要反向审视

v1.0 方案由前端/交互角度出，自然带有以下倾斜：

- 高估了"改交互"的轻量程度，低估了后端 + 数据库工作量
- 假设"轻量 = 老师会用"，但没有数据支撑这个假设
- 缺少对存量历史数据的处理策略
- 对 AI 阶段的描述过于笼统，缺少技术可行性分析

以下是对 v1.0 的 10 个盲点的逐一说明和应对。

### 13.2 十大盲点及应对

| # | 盲点 | 严重程度 | v1.0 的问题 | v1.1 的应对 | 对应章节 |
|:-:|------|:-------:|------------|-----------|:-------:|
| 1 | **工作量误判** | 🔴 高 | 说"改4页"，实际前后端+DB共需改 ~14 个文件，5~8 人天 | 给出逐项文件级估算和依赖关系 | 12 节 |
| 2 | **冷启动空洞** | 🔴 高 | 假设上线即产数据，没处理已有数百条历史记录 | 三步冷启动策略：默认值→引导期→评估期 | 12 节 |
| 3 | **采纳率过于乐观** | 🟡 中 | "批改后弹出"可达 40% 采纳率，但"后弹出"意味着老师已进入下一心态 | 改为"提交时一并选择"；并给出分层应对（>60%/30~60%/10~30%/<10%） | 4、12 节 |
| 4 | **维度标签模糊** | 🟡 中 | 只列了 6 个维度名，没定义边界，老师可能误标 | 给出每个维度的正例/反例表，提高一致性 | 6 节 |
| 5 | **过敏与观察混淆** | 🔴 高 | 把"过敏提醒"和"挑食""吃得少"并列作为可选标签 | 过敏改为系统自动安全提醒，从学生健康档案触发，不属于"观察"范畴 | 5 节 |
| 6 | **"家长可见"使用规范缺失** | 🟡 中 | 只有技术开关，没有使用规范，可能导致老师社交压力 | 补充了 usage guideline：适用范围、48h 时限、10% 比例提醒、前端视觉区分 | 7 节 |
| 7 | **阶段间缺少衔接** | 🔴 高 | 第一阶段"只沉淀"，第三阶段"才确认"，中间无人确认数据 | 增加工作台"待确认"角标 + 成长档案页内的确认操作 | 8、12 节 |
| 8 | **AI 阶段空泛** | 🟡 中 | 说"AI 生成摘要"但无模型/数据量/成本分析 | 补充了 30 条/月/孩子的数据密度下 AI 的可行性边界和限制 | 12 节 |
| 9 | **缺少检索策略** | 🟢 低 | 只提了数据增长，没说怎么检索 | 第二阶段增加按维度/标签/时间筛选 | 本节 |
| 10 | **缺少成功度量** | 🟢 低 | 没定义"怎么算做对了" | 补充了 6 个可量化指标和目标值 | 12 节 |

### 13.3 补充：AI 可行性评估

v1.0 把 AI 部分放在"第二阶段"，但未评估可行性。以下是补充分析：

**环境约束**：

- 当前云端服务器：普通 VPS（nginx + systemd 部署），无 GPU
- 可选方案：

| 方案 | 优点 | 缺点 | 推荐? |
|------|------|------|:----:|
| 调用外部 LLM API | 质量高，实施快 | 成本（token 费用），数据需出服务器 | 🟡 中小机构可接受 |
| 本地部署小模型 | 数据不出域 | 需 GPU，当前服务器不支持 | ❌ 当前不可行 |
| 规则模板生成 | 无成本，可控 | 机械，不自然 | 🟢 第一阶段可用 |

**数据量评估**：

- 稳态预期：30 条/月/孩子的结构化标签数据
- 这足够生成**周报级别**的观察摘要（基于 7~8 条/周）
- 不足以生成有意义的日报（1~2 条/天，过于稀疏）
- 不足以为单个孩子训练个性化模型

**建议的 AI 路线**：

- **第一阶段**（当前）：规则模板——`[孩子名]今天在[场景]表现[标签]` 这种句式拼接，不调用任何模型
- **第二阶段**（数据量充足后）：调用云端 LLM API（如 DeepSeek 或 Claude API）进行摘要生成
- **第三阶段**（可选）：在摘要基础上，提供"成长趋势分析"

### 13.4 补充：第二阶段检索策略

当数据量达到每月数百条后，需要以下检索能力：

| 检索维度 | 前端控件 | 后端要求 |
|---------|---------|---------|
| 按时间段 | 日期范围选择器 | timeline 接口增加 start_date/end_date 参数 |
| 按孩子 | 现有学生选择器 | 已有 |
| 按维度 | 下拉选择 (社交/学习/运动/等) | growth 接口增加 dimension 筛选参数 |
| 按标签类型 | tag 选择器 | 新增 tags 参数 |
| 全文搜索 | 搜索框 | Elasticsearch 或 PostgreSQL `ilike` 简单搜索 |
| 按确认状态 | 已确认/未确认过滤 | 新增 `confirmed` 参数 |

**第一阶段不实现**，数据量在 1000 条以下时前端筛选即可。第二阶段再添加后端索引和筛选接口。

### 13.5 补充：方案 B（当"轻量标签"模式失败时）

如果按以上设计上线 4 周后，标签覆盖率仍低于 10%，说明"轻量可选"这个核心假设失败了。此时应启动方案 B。

**方案 B 核心变更**：

1. **去掉所有分类标签**——不再让老师点"专注/粗心/社交"等细粒度标签
2. **改为"每日班级观察"**——老师每天闭园前写一段自然语言观察，覆盖 2~3 个当天有亮点的孩子
3. **AI 拆解**——这段文字在后端通过规则或 AI 拆解为逐条观察
4. **老师确认**——拆解后的条目由老师在第二天的"待确认"列表中快速确认

**优劣对比**：

| 维度 | 方案 A（标签模式） | 方案 B（自然语言+AI拆解） |
|------|-----------------|------------------------|
| 老师负担 | 每次操作点一下 | 每天写一段话 |
| 数据结构化程度 | 高（预设标签） | 低（需要 AI 解析） |
| 对 AI 的依赖 | 低 | 高 |
| 实施成本 | 中（改 4 个页面） | 高（需 NLP/LLM） |
| 家长理解成本 | 低 | 中 |
| 风险 | 采纳率可能低 | AI 解析可能不准 |

**建议**：以方案 A 为目标优先实施，但在第一阶段结束时进行数据评估。如果覆盖率达标则继续，否则切换方案 B。
